# Module: Gas Station Combo Finder

*(เดิมชื่อ "PTT + 7-Eleven Combo Finder" — v0.5 ขยายให้จับคู่ได้หลายคู่ปั๊ม-ร้าน ไม่ใช่แค่ PTT+7-Eleven อย่างเดียว)*

## หน้าที่
กรองแสดงเฉพาะปั๊มน้ำมันที่มีร้าน/คาเฟ่ในเครืออยู่ในบริเวณเดียวกัน (เช่น ในตัวปั๊มหรือติดกัน) เหมาะกับคนขับรถที่อยากแวะเติมน้ำมันพร้อมช้อปของ/จิบกาแฟทีเดียวจบ ไม่ต้องเสียเวลาแวะสองที่

> ⚠️ **โมดูลนี้เป็น P1 (nice-to-have) ไม่ใช่ P0** เพราะกลไกจับคู่ข้อมูลด้านล่างยังไม่ได้พิสูจน์ว่าแม่นยำพอในทางปฏิบัติ — ต้อง prototype และเช็คผลจริงกับพื้นที่ตัวอย่างก่อนตัดสินใจสร้างเป็นฟีเจอร์เต็มรูปแบบ **ทำทีละคู่** ไม่ใช่ทำทั้ง 3 คู่พร้อมกันตั้งแต่แรก

## Pairing Registry — ตารางคู่ปั๊ม-ร้านที่รองรับ

โมดูลนี้ไม่ hardcode ว่า "PTT คู่กับ 7-Eleven" อีกต่อไป แต่อ่านจากตาราง config เดียวกับ Brand Registry (ดูสเปคหลัก หัวข้อ 4) โดยแต่ละแบรนด์ร้าน/คาเฟ่ที่มีคู่ปั๊มน้ำมันชัดเจนจะมี field `fuelBrandPair` เพิ่มเข้ามา:

| ปั๊มน้ำมัน | ร้าน/คาเฟ่ในเครือที่มักเจอ |
|---|---|
| PTT | 7-Eleven, Café Amazon |
| บางจาก (Bangchak) | อินทนิล (Inthanin) |
| PT (PTG) | พันธุ์ไทย (Punthai Coffee) |

**Black Canyon และ Chao Doi ไม่มีในตารางนี้** — สองแบรนด์นี้ไม่มีความสัมพันธ์แบบผูกขาดกับปั๊มน้ำมันแบรนด์ใดแบรนด์หนึ่ง (พบทั่วไปในห้าง/อาคารสำนักงานมากกว่าปั๊ม) จึงค้นหาได้ปกติผ่าน Map/List Store แต่ไม่เข้าโมดูลนี้

## ทำไมถึงซับซ้อนกว่าโมดูลอื่น
OSM **ไม่มี tag มาตรฐาน** ที่บอกตรงๆ ว่า "ปั๊มน้ำมันโหนดนี้มีร้าน X อยู่ข้างใน" ปั๊มกับร้าน/คาเฟ่ถูก map เป็นสอง node แยกกันอิสระ (`amenity=fuel` กับ `shop=convenience`/`amenity=cafe`) ไม่มีความสัมพันธ์ทาง data เชื่อมกันเลย ต้องคำนวณจับคู่เอาเองฝั่ง client — แต่เพราะ logic การจับคู่เป็นแบบเดียวกันทุกคู่ (ต่างกันแค่ brand tag ที่ระบุ) เขียนฟังก์ชันเดียวแล้ว reuse ได้กับทุกแถวใน Pairing Registry

## Flow การทำงาน (ทีละขั้น)

1. **เลือกคู่ปั๊มที่จะแสดง** — ค่าเริ่มต้นแสดงทุกคู่ที่ prototype ผ่านแล้ว (ดู Open Questions) หรือให้ user ติ๊กเลือกคู่ที่สนใจ (เช่น เฉพาะ "บางจาก+อินทนิล")
2. **ยิง Overpass query สองชุดต่อคู่** ในรัศมีที่เลือก (ค่าเริ่มต้นกว้างกว่าโมดูลอื่น เช่น 5 กม. เพราะปั๊มน้ำมันกระจายตัวห่างกว่าร้านสะดวกซื้อทั่วไป) — ตัวอย่างคู่ PTT+7-Eleven:
   - Query A (ปั๊ม): `node["amenity"="fuel"]["brand"~"PTT",i](around:{radius_m},{lat},{lng});`
   - Query B (ร้านในเครือ): `node["shop"="convenience"]["brand"~"7-Eleven",i](around:{radius_m},{lat},{lng});`
   
   ทำแบบเดียวกันสำหรับคู่บางจาก+อินทนิล และ PT+พันธุ์ไทย เปลี่ยนแค่ค่า `brand` และ tag ประเภทร้าน (`amenity=cafe` แทน `shop=convenience` สำหรับคาเฟ่)
3. **จับคู่ฝั่ง client (proximity matching)** — สำหรับปั๊มแต่ละแห่งใน Query A ให้คำนวณระยะทาง (Haversine) ไปยังร้านในเครือทุกร้านใน Query B ของคู่เดียวกัน ถ้ามีร้านใดอยู่ในระยะ **threshold ที่กำหนด (แนะนำเริ่มทดสอบที่ ~50-80 เมตร ทุกคู่ใช้ threshold เดียวกันเป็นจุดเริ่มต้น)** ให้ถือว่าปั๊มนั้น "มีร้านนี้ในตัว" และจับคู่ไว้
4. **กรองเฉพาะปั๊มที่จับคู่สำเร็จ** — แสดงเฉพาะปั๊มที่มีร้านในเครือจับคู่ได้เท่านั้น ปั๊มที่ไม่มีร้านในระยะ threshold จะถูกซ่อนจากรายการนี้
5. **Render เป็น list/map** เหมือนโมดูลอื่น — แสดงระยะทางจาก user, ชื่อปั๊ม, **badge บอกว่ามีร้านอะไรในเครือ** (อาจมีมากกว่า 1 อย่างถ้าปั๊มเดียวมีทั้งร้านสะดวกซื้อและคาเฟ่ เช่น PTT บางสาขามีทั้ง 7-Eleven และ Café Amazon), สิ่งอำนวยความสะดวก, ปุ่มนำทาง

## ข้อมูลที่แสดงต่อการ์ด
- ชื่อปั๊ม + แบรนด์ปั๊ม + ระยะทางจาก user
- Badge ร้าน/คาเฟ่ในเครือที่จับคู่ได้ (เช่น "มี 7-Eleven", "มี Café Amazon" — มาจากผลจับคู่ ไม่ใช่ tag ตรงๆ)
- สิ่งอำนวยความสะดวกเท่าที่มีใน OSM tag: EV charger (`amenity=charging_station` ใกล้เคียง), ห้องน้ำ (`toilets=yes`), ที่จอดรถ
- เวลาเปิด-ปิด (จาก `opening_hours` ถ้ามี)
- ปุ่มนำทาง — deep link เหมือนโมดูลอื่น

## หมายเหตุทางเทคนิค / ความเสี่ยง (สำคัญ — อ่านก่อนพัฒนา)

- **Threshold ระยะทางยังไม่ได้ทดสอบจริงในคู่ไหนเลย** — ตัวเลข 50-80 เมตรเป็นค่าประมาณตามสามัญสำนึก (ขนาดปั๊มทั่วไป) ไม่ใช่ค่าที่ verify กับข้อมูลจริงแล้ว ต้องดึงข้อมูลตัวอย่างจากพื้นที่จริงมาเช็คว่า threshold นี้จับคู่ถูกจริงกี่ % (false positive: ปั๊มกับร้านที่ไม่เกี่ยวกันแต่บังเอิญอยู่ใกล้กัน / false negative: ปั๊มที่มีร้านจริงแต่ node ห่างกันเกิน threshold เพราะคนละคน map พิกัดไม่ตรงกัน) — **แต่ละคู่อาจต้องปรับ threshold ต่างกัน** เพราะขนาด/lay out ปั๊มแต่ละแบรนด์ไม่เท่ากัน
- **ความครบถ้วนของ tag `brand`** — ปั๊มหรือร้านบางจุดอาจไม่ได้ใส่ tag `brand` ไว้ครบ (ใส่แค่ `name` เฉยๆ) ทำให้ query กรองไม่เจอทั้งที่มีอยู่จริง เป็นปัญหาความครบถ้วนของ OSM data โดยรวม ไม่ใช่บั๊กของ logic — คาดว่า **PTT+7-Eleven มีข้อมูลครบสุดในสามคู่** (สาขาเยอะที่สุด) ส่วนบางจาก+อินทนิล และ PT+พันธุ์ไทย ยังไม่ได้เช็ค
- **แนะนำขั้นตอนก่อนสร้างจริง**: ใช้ overpass-turbo.eu ทดสอบ query ทั้งสองชุดของแต่ละคู่ในพื้นที่ตัวอย่าง (เช่น กรุงเทพฯ 2-3 เขต) แล้วเช็คด้วยตาว่าผลจับคู่ตรงกับความจริงแค่ไหน ก่อนเขียนเป็นฟีเจอร์ในแอป — **แนะนำเริ่ม prototype จากคู่ PTT+7-Eleven ก่อน** เพราะน่าจะมีข้อมูลครบสุด ได้ผลดีแล้วค่อยขยายไปคู่อื่น
- ถ้าพิสูจน์แล้วว่าคู่ไหนจับคู่ไม่แม่นพอ ทางเลือกสำรองคือให้ user ช่วย confirm/report เอง (crowd-source แบบเบาๆ ผ่าน localStorage ส่วนตัว ไม่ใช่ DB กลาง) แต่ยังไม่ใช่ scope ของ v1 — หรือถอดคู่นั้นออกจาก Pairing Registry ชั่วคราวถ้าคุณภาพไม่ผ่าน
