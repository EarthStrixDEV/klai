# Module: Emergency Contacts (สมุดเบอร์โทรฉุกเฉิน)

## หน้าที่
หน้าเนื้อหา static ล้วนๆ เหมือนหน้า About — ไม่มี dynamic data, ไม่มี API call, ไม่ผูกกับ Brand Registry — รวมเบอร์โทรฉุกเฉินหลักของประเทศไทย จัดกลุ่มเป็นหมวดให้กดโทรได้เร็วตอนขับรถอยู่ เป็นแท็บแยกในเมนูหลัก (ไม่ใช่ section ย่อยในหน้า About) เพื่อให้เข้าถึงได้เร็วที่สุด

## ทำไมถึงอยู่ใน Klai
Klai ถูกใช้งานส่วนใหญ่ตอน user กำลังขับรถ/เดินทางหาร้าน/ปั๊มน้ำมันอยู่แล้ว — ถ้าเกิดเหตุฉุกเฉินระหว่างทาง (อุบัติเหตุ, เจ็บป่วยเฉียบพลัน) การมีเบอร์พร้อมกดในแอปเดียวกันมีประโยชน์จริง และต้นทุนสร้างต่ำมากเพราะเป็น static content ล้วนๆ ไม่ต้องพึ่ง OSM/Overpass เหมือนโมดูลอื่น

## โครงสร้างหน้า
1. **Alert banner บนสุด** — โทนสีแดง/danger เด่นชัด ดึง 2 เบอร์สำคัญสุด (191, 1669) ขึ้นมาเป็นปุ่มใหญ่ก่อนรายการกลุ่มอื่น
2. **รายการแบบจัดกลุ่ม** (4 กลุ่มด้านบน) — แต่ละรายการมี: ชื่อ/คำอธิบาย, เบอร์ (ตัวใหญ่ อ่านง่าย), ปุ่ม "โทร"
3. **Disclaimer ปิดท้าย** (ดูหัวข้อถัดไป)

## ปุ่ม "โทร"
ใช้ `tel:{number}` link ต่อรายการ (เช่น `tel:191`) — กดแล้วเปิดแอปโทรศัพท์พร้อมเบอร์กรอกไว้ให้ ไม่ต้องมี backend/API ใดๆ ทำงานได้ทันทีบนมือถือ (บน desktop browser อาจไม่ trigger อะไรถ้าเครื่องไม่มีแอปโทรศัพท์ผูกไว้ — เป็นข้อจำกัดปกติของ `tel:` scheme ไม่ใช่บั๊ก)

## ข้อความ Disclaimer (ใช้ตรงตามนี้)
> รายชื่อเบอร์โทรฉุกเฉินนี้รวบรวมจากแหล่งข้อมูลสาธารณะเพื่อความสะดวก **ไม่ใช่ข้อมูลที่ Klai รับรองความถูกต้อง 100%** เบอร์บางรายการอาจมีการเปลี่ยนแปลงได้ กรุณาตรวจสอบเบอร์อีกครั้งก่อนใช้งานในสถานการณ์ฉุกเฉินจริง

**เหตุผล**: เบอร์เหล่านี้เป็น static content ต้องอัปเดตด้วยมือทุกครั้งถ้ามีการเปลี่ยนแปลงจริง ไม่มีกลไกเช็คอัตโนมัติเหมือนข้อมูลร้านที่ดึงสดจาก OSM — ต้องกันความเข้าใจผิดว่า Klai การันตีความถูกต้อง 100% ไว้ด้วย

## หมายเหตุทางเทคนิค
- หน้านี้ไม่มี logic ซับซ้อน เป็น static content เหมือนหน้า About — build ง่าย ไม่มี dependency กับ Brand Registry/Overpass/GPS เลย
- **เป็นรายชื่อระดับประเทศ ไม่ทำ location-aware filtering** — เบอร์มูลนิธิบางเบอร์ (เช่น 1646 ศูนย์เอราวัณ, 1418 ป่อเต็กตึ๊ง) เป็นของกรุงเทพฯ เป็นหลัก แต่ยังใส่ไว้ในรายการเดียวกันทั้งหมดเพื่อคงความง่ายของสถาปัตยกรรม "0 backend" — ถ้าจะทำ location-aware ในอนาคตต้องมี backend/data source เพิ่ม ซึ่งขัดกับหลักการปัจจุบันของโปรเจกต์
- ควรมี "อัปเดตล่าสุดเมื่อ" กำกับไว้ท้ายหน้า (เช่น "ข้อมูล ณ ก.ย. 2569") ให้ user รู้ว่าอิงข้อมูลตอนไหน
