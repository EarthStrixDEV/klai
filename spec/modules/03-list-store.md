# Module: List Store

## หน้าที่
แสดงร้าน (จากแบรนด์ที่เลือกไว้) ทั้งหมดรอบตัว user เป็นรายการ (list) เรียงตามระยะทาง พร้อมเครื่องมือค้นหา/filter/sort ให้ครบ — เหมาะกับคนที่อยากดูข้อมูลแบบละเอียดกว่าแผนที่ (เช่น เทียบเวลาเปิด-ปิดหลายร้านพร้อมกัน) รองรับ **เลือกได้หลายแบรนด์พร้อมกัน** เหมือนหน้า Map ตั้งแต่ v0.5

## ใช้ข้อมูลชุดเดียวกับ Map (รวมทั้งชุดแบรนด์ที่เลือก)
หน้านี้ **ไม่ยิง Overpass query ใหม่ทุกครั้ง** ถ้า user มาจากหน้า Map (หรือกำลังจะสลับไป) ด้วยพิกัด/รัศมี/ชุดแบรนด์เดิม — ใช้ผลลัพธ์ที่ cache ไว้ใน memory ร่วมกัน (ดู `02-map.md` หัวข้อหมายเหตุทางเทคนิค) ยิง query ใหม่เฉพาะตอนพิกัดเปลี่ยน (เช่น กด GPS ใหม่), รัศมีเปลี่ยน, หรือ **ชุดแบรนด์ที่ติ๊กเปลี่ยน** — brand filter chip เป็น component เดียวกับหน้า Map ใช้ state ร่วมกัน สลับหน้าไปมาไม่ต้องติ๊กใหม่

## Flow การทำงาน (ทีละขั้น)

1. **โหลดข้อมูล** — ใช้ cache จาก Map ถ้ามีและยังไม่ stale, ไม่งั้นยิง Overpass query ตาม pattern เดียวกับ Map module
2. **คำนวณระยะทาง + เรียงลำดับ** — Haversine จาก user ไปแต่ละร้าน, sort จากใกล้→ไกล เป็นค่าเริ่มต้น
3. **Render การ์ดร้าน** ทีละใบตามลำดับที่ sort ไว้ (ดูโครงสร้างการ์ดด้านล่าง)
4. **ผู้ใช้ปรับ search/filter/sort** → ทุกการกระทำเป็นการกรอง/เรียงข้อมูล **ฝั่ง client ล้วนๆ** จาก array ที่โหลดมาแล้ว ไม่มีการยิง request ใหม่ (ยกเว้นเปลี่ยนรัศมี — ดูข้อ 5)
5. **เปลี่ยน radius chip** → ต้องยิง Overpass query ใหม่ด้วยรัศมีใหม่ (ข้อมูลนอกรัศมีเดิมยังไม่เคยถูกดึงมา) แล้วเริ่ม flow ใหม่ตั้งแต่ข้อ 1

## โครงสร้างการ์ดแต่ละร้าน
แต่ละการ์ดแสดง:
- **Badge สีบอกแบรนด์** (สีเดียวกับ pin บนแผนที่ ตาม Brand Registry) + ชื่อร้าน + เลขสาขา (ถ้ามีใน tag)
- **Badge ระยะทาง** (เช่น "350 ม.")
- ที่อยู่แบบย่อ (จาก `addr:*` tag ถ้ามี ไม่งั้น fallback เป็นชื่อถนน/ย่านจาก reverse-geocode คร่าวๆ หรือซ่อน field นี้ไปเลย)
- Tag สถานะ เช่น "เปิด 24 ชม." (ถ้ามีข้อมูล — ดู caveat ด้านล่าง)
- ปุ่ม "นำทาง" → deep link Google Maps เหมือน Map module

> การ์ดของแบรนด์ประเภท "ปั๊มน้ำมัน" (PTT) ใช้ไอคอนหัวจ่ายน้ำมันแทนไอคอนร้านค้า เพราะเป็นคนละ category กับร้านสะดวกซื้อ/คาเฟ่ — ยังใช้โครงสร้างการ์ดเดียวกันทุกอย่าง แค่สลับไอคอนตามประเภทที่ Brand Registry กำหนด

## เครื่องมือค้นหา / Filter / Sort

| เครื่องมือ | การทำงาน |
|---|---|
| ช่องค้นหา | filter ฝั่ง client แบบ match ชื่อร้าน/ที่อยู่/ย่าน ข้ามทุกแบรนด์ที่แสดงอยู่ (substring match, ไม่ case-sensitive) |
| **Filter แบรนด์ (multi-select)** | chip เดียวกับหน้า Map — ติ๊ก/ถอดติ๊กแบรนด์ที่อยากเห็นในลิสต์ ถ้าติ๊กแบรนด์ที่ยังไม่เคยยิง query มาก่อน ต้องยิง Overpass เพิ่ม |
| Filter รัศมี (500ม./1กม./3กม./5กม.) | รัศมีที่กว้างขึ้นต้องยิง query ใหม่ (ดูข้อ 5 ด้านบน), รัศมีที่แคบลงกว่าที่โหลดไว้แล้วกรองฝั่ง client ได้เลยไม่ต้องยิงใหม่ |
| Filter เพิ่มเติม (เปิด 24 ชม. / มีที่จอดรถ / มี ATM / อยู่ในปั๊มน้ำมัน) | กรองจาก OSM tag ที่มีอยู่ (`opening_hours`, `parking`, `atm`, ฯลฯ) — **ข้อมูลพวกนี้ไม่ครบทุกร้านใน OSM จริง** ร้านที่ไม่มี tag จะไม่ถูกนับว่า "มี" (ไม่ใช่ว่า "ไม่มี") ต้องสื่อสารกับ user ผ่าน UI ว่านี่คือข้อมูลเท่าที่มีคน map ไว้ ไม่ใช่ความจริง 100% |
| Filter "อยู่ในปั๊มน้ำมัน" | ใช้ผลลัพธ์เดียวกับโมดูล Gas Station Combo Finder (ดู `05-gas-station-combo.md`) — ครอบคลุมทุกคู่ปั๊ม-ร้านใน registry ไม่ใช่แค่ PTT อีกต่อไป ถ้ายังไม่ได้ query ฝั่งนั้นมา ต้องยิงเพิ่ม |
| Sort dropdown | ค่าเริ่มต้น "ใกล้สุดก่อน" (ตามระยะทาง) — อาจเพิ่ม "ชื่อ A-Z" หรือ "แบรนด์" เป็นตัวเลือกเสริมได้ ไม่จำเป็นสำหรับ MVP |

## Floating action: "ดูบนแผนที่"
ปุ่มลอยมุมล่าง สลับไปหน้า Map พร้อมพิกัด/รัศมี/ผลลัพธ์ปัจจุบัน (ใช้ cache เดิม ไม่ยิง query ซ้ำ) — ช่วยให้ user สลับมุมมอง list ⇄ map ได้ลื่นๆ โดยไม่เสียสถานะการค้นหา

## Error / Empty state
- ไม่พบร้านตรงเงื่อนไข filter ปัจจุบัน: แสดงข้อความ "ไม่พบร้านที่ตรงกับตัวกรอง" พร้อมปุ่ม "ล้างตัวกรองทั้งหมด"
- Overpass fetch fail: ใช้ error state เดียวกับ Map module (ข้อความ + ปุ่ม retry)

## หมายเหตุทางเทคนิค
- Filter เพิ่มเติม (24 ชม./ที่จอดรถ/ATM) ควรมี tooltip หรือข้อความกำกับเล็กๆ ว่า "ข้อมูลอ้างอิงจาก OpenStreetMap อาจไม่ครบทุกสาขา" กัน user เข้าใจผิดว่าระบบผิดถ้าร้านที่รู้ว่าเปิด 24 ชม. จริงไม่ขึ้นในผลกรอง
- ถ้าจำนวนร้านในรัศมีเยอะมาก (เช่น รัศมี 5 กม. ในกรุงเทพฯ ติ๊กหลายแบรนด์พร้อมกัน) ควร render แบบ lazy/virtualized list กัน list ยาวเกินจน scroll กระตุก — เป็น performance optimization ไม่ใช่ P0 แต่ควรกันไว้ตั้งแต่โครงสร้าง component
- ความครบถ้วนของข้อมูลใน OSM ต่างกันมากระหว่างแบรนด์ (7-Eleven ครบสุด, แบรนด์สาขาน้อยอย่าง Chao Doi อาจครบน้อยกว่า) — ถ้าติ๊กหลายแบรนด์แล้วบางแบรนด์ผลลัพธ์น้อยผิดปกติ ไม่ใช่บั๊ก แต่เป็นข้อจำกัดของข้อมูลต้นทาง
